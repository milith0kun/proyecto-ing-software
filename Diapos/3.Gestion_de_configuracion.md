## Resumen de la presentación

La gestión de configuración permite identificar qué archivos, pruebas, documentación y dependencias forman parte de una entrega; establecer una versión aprobada que sirva como referencia; y controlar los cambios con responsables, revisión y evidencia. El flujo colaborativo presentado va desde una necesidad registrada en un issue, pasa por una rama y un Pull Request revisado, y termina con pruebas, integración y cumplimiento de la Definition of Done (DoD).

La idea que se repite es que guardar un archivo, crear un commit, crear un tag o cerrar un Pull Request son acciones distintas. Para considerar un cambio completo, el equipo debe poder explicar qué cambió, por qué, quién lo revisó y cómo comprobó el resultado.

### 2. Gestión de configuración — páginas 4–10

- **Página 4 — Caso real:** un reporte del proyecto `pytest` muestra que cambió el nombre de un archivo, pero una instrucción seguía haciendo referencia al nombre anterior. La diapositiva pregunta: «¿Basta con guardar el código?». La captura corresponde al issue [pytest #13033](https://github.com/pytest-dev/pytest/issues/13033).
- **Página 5 — Pregunta central:** ¿qué se debe conservar para reconstruir una entrega? La respuesta de la diapositiva es identificar versiones, acordar una referencia y controlar los cambios.
- **Página 6 — Ítems de configuración:** cada elemento necesita identidad, versión, ubicación y responsable. La presentación enumera:
  - Código, por ejemplo `src/`.
  - Pruebas, por ejemplo `tests/`.
  - Entorno y dependencias, por ejemplo el archivo de bloqueo de paquetes (`package-lock.json`).
  - Acuerdos y documentación, por ejemplo `docs/`.
  - También requisitos, datos de prueba, scripts y configuración de automatización.
- **Página 7 — Línea base:** es un conjunto identificado y aprobado que sirve de referencia. Debe especificar:
  - **Identidad:** versión y commit de referencia.
  - **Contenido:** código, pruebas y documentos incluidos.
  - **Reproducción:** dependencias e instrucciones.
  - **Aprobación:** quién aprobó, cuándo y con qué evidencia.

  Una etiqueta de Git puede señalar una versión, pero el acuerdo de aprobación es lo que la convierte en línea base.
- **Página 8 — Control de cambios:** el cambio se registra como una decisión y no queda perdido en un mensaje. El flujo mostrado es: **proponer (issue) → evaluar impacto → decidir/aprobar → aplicar y verificar → integrar y registrar**. Se evalúa el impacto en comportamiento, interfaces, pruebas, documentación y entrega. Si se rechaza o posterga, también se registra la razón.
- **Página 9 — Trazabilidad:** los enlaces deben permitir recorrer la necesidad hasta la implementación y regresar. El ejemplo visual une **issue #13033 → Pull Request #13034 → commit `0526346` → integración `9fc8a3e`**. Para el proyecto, la diapositiva pide añadir también la prueba y la versión que contienen el cambio.
- **Página 10 — Ejercicio de inventario y línea base:**
  1. Elegir cuatro ítems y anotar ruta, versión y responsable.
  2. Definir qué evidencia permitirá aprobar la línea base.
  3. Acordar quién autoriza cambios que afecten requisitos.

  **Evidencia solicitada:** `docs/configuracion.md`, con inventario y regla de aprobación. La pregunta guía es si otro equipo podría reconstruir la próxima demostración.

### 3. Control de versiones — páginas 11–21

- **Página 11 — Introducción:** después de definir qué conservar, la pregunta es cómo cambiar sin perder la historia. Se presentan repositorio, commit, branch, merge y tag.
- **Página 12 — Repositorio:** Git registra versiones y sus relaciones; GitHub aloja el remoto, issues y revisiones. La imagen muestra un repositorio real de `pytest`. También aparece el intercambio entre local y remoto mediante `fetch` y `push`.
- **Página 13 — Commit:** el recorrido es **directorio de trabajo → preparación (staging) → repositorio local → repositorio remoto**, con `git add`, `git commit` y `git push`. Un commit coherente representa una intención, tiene un mensaje claro y contiene cambios revisados. Antes de confirmar, se sugieren `git status` y `git diff --staged`. Guardar un archivo, crear un commit y hacer push son acciones distintas.
- **Página 14 — Branch y merge:** una rama es una referencia móvil; el merge integra historias. El diagrama muestra una rama `feature/42-reservar` que avanza aparte y luego se incorpora a `main` mediante un commit de merge con dos padres. La rama aísla el trabajo; la revisión decide cuándo integrarlo.
- **Página 15 — Conflicto de merge:** dos ramas contienen reglas distintas para una reserva (límite de dos horas frente a límite de una hora y reglas diferentes para ampliar o repartir turnos). El equipo debe leer ambas intenciones, acordar la regla, editar y comprobar, y confirmar la resolución. Resolver el conflicto de texto no demuestra que el comportamiento sea correcto.
- **Página 16 — Tag, release y línea base:**
  - **Tag:** localiza un punto de la historia, por ejemplo `v0.1.0` asociado a un commit.
  - **Release:** publica notas y artefactos asociados a una versión.
  - **Línea base:** acuerda qué conjunto está aprobado y cómo se controla su cambio.

  La aplicación sugerida es una etiqueta, un manifiesto de versiones y una aprobación.
- **Página 17 — Infografía «Línea base en software»:** ilustra que una línea base es una versión aprobada y estable del producto o conjunto de artefactos. Enumera código fuente, documentación, pruebas y configuración. El esquema muestra cambios locales (corrección, nueva función y ajuste) que se registran en commits pequeños; una versión estable aprobada pasa a ser línea base y puede identificarse con un tag. Resume la relación así: **varios commits construyen una versión; al aprobarse, puede convertirse en línea base y marcarse con un tag**.
- **Página 18 — Captura de tags:** imagen del repositorio `git/git`, con etiquetas verificadas de versiones como `v2.56.0`, `v2.56.0-rc2` y `v2.56.0-rc1`. Sirve como ejemplo visual de etiquetas que apuntan a versiones concretas.
- **Página 19 — Estrategia Git Flow:** el diagrama presenta ramas `main`, `develop`, `feature`, `hotfix` y `release`. Reglas de la lámina:
  - `main` contiene código de producción.
  - `develop` contiene código de desarrollo.
  - Las ramas `feature` salen de `develop`.
  - Las ramas `hotfix` salen de `main`.
  - Las ramas `release` salen de `develop`.

  Incluye un enlace a [Git Flow de JetBrains](https://blog.jetbrains.com/space/2023/04/18/space-git-flow/#github-flow).
- **Página 20 — Flujo de GitHub:** el dibujo separa `main` de una rama de funcionalidad. Los cambios se trabajan en la rama, se abre un Pull Request para conversar y revisar commits, y después se fusionan. La diapositiva indica que `main` contiene código de producción; las ramas `feature` son independientes; los Pull Requests pasan por las reglas de protección; y las releases se crean desde `main` y se etiquetan.
- **Página 21 — Ejercicio de una rama:**
  1. Elegir una estrategia de ramas, abrir o clonar el repositorio y crear `docs/entorno`.
  2. Editar el README, revisar el diff y crear un commit.
  3. Publicar la rama y localizar el commit en el remoto.

  **Evidencia solicitada:** URL del commit y nombre de la rama.

### 4. Desarrollo colaborativo — páginas 22–28

- **Página 22 — Introducción:** un cambio está listo; se pregunta quién debe entenderlo antes de unirlo. Se anuncian issues, Pull Requests, revisión y mensajes con intención.
- **Página 23 — Issues:** «No funciona» no permite reproducir ni comprobar una solución. Un issue útil describe el problema, incluye contexto y pasos para reproducir, resultado actual y esperado, criterios de aceptación, responsable y prioridad. Debe responder qué problema existe y cómo se sabrá que quedó resuelto.
- **Página 24 — Pull Request:** propone unir una rama, explica el cambio e invita a revisarlo. La captura del PR #13034 de `pytest` ilustra que la conversación queda conservada en el Pull Request.
- **Página 25 — Infografía del proceso de Pull Request:** muestra nueve pasos y un ciclo de retroalimentación:
  1. **Crear rama:** por ejemplo `feature/nueva-funcion`, a partir de `main` o `develop`.
  2. **Desarrollar y hacer commits:** escribir código en la rama y registrar avances con mensajes claros.
  3. **Publicar la rama:** hacer `push` al remoto (GitHub, GitLab o Bitbucket).
  4. **Abrir Pull Request:** pedir fusionar la rama con `main`, describir qué se hizo, por qué y cómo probarlo, y asignar revisores.
  5. **Ejecutar pruebas automáticas:** integración continua para pruebas unitarias, lint y seguridad.
  6. **Revisar el código:** los revisores analizan el código y comentan; si hay observaciones, el autor corrige y vuelve a publicar. El PR se actualiza.
  7. **Aprobar:** los revisores aprueban cuando se cumplen estándares y pasan las pruebas.
  8. **Fusionar (merge):** integrar la rama en `main`.
  9. **Desplegar y cerrar:** desplegar a staging o producción y, si corresponde, eliminar la rama.

  La idea clave de la imagen es que un Pull Request también documenta cambios, activa pruebas y facilita la colaboración.
- **Página 26 — Code Review:** revisar el diff y pedir evidencia. La captura muestra la corrección de la ruta configurada para `blame.ignoreRevsFile`: de `.gitblameignore` a `.git-blame-ignore-revs`. La revisión debe preguntar:
  - **Correctitud:** ¿la instrucción usa el archivo correcto?
  - **Impacto:** ¿queda otra referencia desactualizada?
  - **Evidencia:** ¿cómo comprobó el autor que funciona?
- **Página 27 — Convenciones de commits:** formato `tipo(ámbito): descripción`. Ejemplo: `docs(entorno): explica cómo ejecutar las pruebas`. «cambios» no comunica intención; `fix(reservas): evita aceptar horarios ocupados` sí la comunica. El equipo debe acordar idioma, tipos y tamaño del cambio, y el mensaje debe reflejar el diff. Se cita Conventional Commits 1.0.0.
- **Página 28 — Ejercicio de revisión:** abrir un Pull Request desde la rama anterior; crear un issue y enlazarlo al PR con problema, cambio y verificación; pedir que otra persona revise el diff y deje un comentario concreto; corregir o responder y registrar la decisión.

  **Evidencia solicitada:** PR enlazado al issue, comentario y respuesta.

### 5. Gestión visual y Definition of Done — páginas 29–33

- **Página 29 — Introducción:** si la revisión existe, el equipo necesita saber qué está esperando. Se presentan tablero, estados del flujo y Definition of Done.
- **Página 30 — Tablero de ejemplo:** una captura de un proyecto de plataforma web muestra cuatro columnas: **Pendiente, En desarrollo, En revisión y Hecho**. Las tarjetas tienen ejemplos de reglas, reserva, README y entorno. En la parte inferior aparecen las condiciones de avance: **entrada clara → cambio activo → Pull Request y evidencia → DoD cumplida**. También indica que un bloqueo debe mostrarse en la tarjeta, tener causa explícita y una persona que ayude a resolverlo.
- **Página 31 — Foto de tablero físico:** ejemplo visual de un tablero Kanban con columnas rotuladas «To Do», «Doing» y «Done», y notas adhesivas de varios colores. Los textos de las notas no son suficientemente legibles en el PDF; la imagen se usa para mostrar la distribución visual del trabajo.
- **Página 32 — Definition of Done:** distingue criterios de aceptación de la definición de terminado.
  - Criterio de aceptación de una reserva: si el horario ya está ocupado, el sistema rechaza la solicitud.
  - La DoD de ejemplo exige pruebas pertinentes aprobadas, revisión humana resuelta, documentación actualizada, issue/PR/commit enlazados e integración en la rama acordada.

  «Hecho» significa evidencia verificable de calidad compartida. Se cita la Scrum Guide de 2020.

### 6. IA en repositorios — páginas 34–38

- **Página 34 — Principio general:** la IA puede explicar y proponer; el equipo debe poder comprobar. Se presenta como ayuda para entender, documentar y revisar cambios.
- **Página 35 — Explicación de código:** prompt sugerido: «Explica esta función en este commit. Señala entradas, salidas y efectos. Cita líneas y distingue hechos de supuestos». Después hay que abrir los archivos citados, seguir una entrada concreta, ejecutar un caso límite y corregir lo que no se sostenga. Si falta contexto, la respuesta debe reconocerlo y pedirlo.
- **Página 36 — Mensajes y resúmenes asistidos:**
  - **Commit:** entrada: diff preparado; salida: intención breve. Prompt: «Propón un mensaje según nuestra convención, solo para este diff».
  - **Pull Request:** entrada: diff, issue y resultados; salida: qué cambió, por qué y cómo se verificó. Prompt: «Resume y distingue pruebas ejecutadas de pendientes».

  La persona autora debe contrastar cada afirmación antes de publicarla.
- **Página 37 — Code Review asistido:** flujo ilustrado: IA señala un posible fallo → una persona lo reproduce → el equipo acepta, corrige o descarta → se ejecutan pruebas y revisión. Un hallazgo útil indica archivo, línea, escenario y consecuencia. La decisión trazable registra motivo, cambio aplicado y evidencia de validación. Una recomendación convincente puede ser incorrecta; la aprobación es humana.
- **Página 38 — Ejercicio sobre recomendación de IA:** ante la sugerencia de eliminar una validación porque «el front-end ya la hace», identificar el supuesto, diseñar una comprobación que lo confirme o refute y registrar aceptar, modificar o rechazar con una razón.

  **Evidencia solicitada:** decisión en el PR; si no se usó IA, registrar «sin uso».

### 7. Entorno colaborativo y cierre — páginas 39–46

- **Página 39 — Entregable del entorno colaborativo:**
  - **Repositorio:** README, estructura, inventario y reglas de cambio.
  - **Tablero:** issues reales, responsables, estados y políticas.
  - **Workflow:** ramas, commits, PR, revisión e integración.
  - **DoD:** criterios verificables y evidencia de cumplimiento.

  Se pide un enlace principal desde el cual pueda recorrerse toda la evidencia.
- **Página 40 — Workflow propuesto:** issue con criterios → rama corta con commits → PR con pruebas y revisión → integración con DoD. Los roles son autor (explica y verifica), revisor (contrasta el cambio), equipo (resuelve el impacto) e integrador (comprueba acuerdos). Cada entrega conserva versión identificada, línea base y evidencia.
- **Página 41 — Taller:** integrar inventario y acuerdos para que README sea el punto de entrada; completar tablero, workflow y DoD con políticas y responsables; recorrer un cambio pequeño de issue a rama, PR y revisión; comprobar enlaces y reconstrucción para tener una versión identificada y una demostración lista. El equipo debe mostrar qué adaptó, por qué y cómo se verifica.
- **Página 42 — Revisión entre equipos:** el otro equipo debe poder clonar el repositorio y orientarse; relacionar tablero, trabajo y bloqueos; seguir un cambio hasta su revisión; y reconocer evidencias de la DoD. La retroalimentación debe incluir una fortaleza y una mejora concreta.
- **Página 43 — Comprobación «¿Qué falta para confiar?»:**
  - Versiones: guardé el archivo; ¿ya existe un commit?
  - Gestión visual: cerré el PR; ¿puedo mover la tarjeta a Hecho?
  - Configuración: creé un tag; ¿ya aprobé una línea base?
  - IA: dice que pasan los tests; ¿qué evidencia debo pedir?

  Se debe responder con una condición comprobable, no solo «sí» o «no».
- **Página 44 — Cierre:** para explicar un cambio hay que poder decir qué cambió, por qué, quién lo revisó y cómo se comprobó. El recorrido se sostiene con repositorio, tablero, workflow y DoD.

## Ideas para aplicar después a CGB Academy

Estas son propuestas derivadas del material; todavía requieren contrastarse con el equipo, los usuarios y el backlog de Jira.

1. **Vincular necesidad y evidencia:** registrar en cada historia la necesidad o problema del stakeholder, sus criterios de aceptación y la evidencia con la que se verificó. Relacionar la historia de Jira con el Pull Request, commits y pruebas correspondientes.
2. **Mejorar la trazabilidad del trabajo de la actividad:** las historias revisadas en Jira deberían tener prioridad, criterios observables, tareas técnicas y una referencia a la necesidad encontrada. Registrar por separado si la necesidad es evidencia de entrevista o una hipótesis pendiente.
3. **Definir una regla de aprobación:** acordar quién puede aceptar cambios que afecten requisitos y qué debe revisarse: comportamiento, interfaces, pruebas, documentación y entrega. Conservar la razón cuando un cambio se rechace o postergue.
4. **Acordar condiciones para considerar una historia terminada:** usar una DoD breve y comprobable que incluya criterios de aceptación satisfechos, pruebas pertinentes, revisión resuelta, documentación actualizada y enlaces entre issue, PR y commit; integrar en la rama acordada por el equipo.
5. **Conservar una entrega reproducible:** identificar el commit de la versión y documentar código, pruebas, dependencias e instrucciones necesarias para reconstruirla. Si el equipo aprueba una versión, registrar quién la aprobó y la evidencia.
6. **Revisar cambios con evidencia:** al revisar una historia, comprobar el diff, buscar referencias que puedan quedar desactualizadas y pedir la prueba del comportamiento. Una resolución de conflicto textual no sustituye la validación funcional.
7. **Usar IA como apoyo revisable:** se puede pedir que redacte un mensaje de commit, resuma un PR o explique código; la persona debe confirmar las afirmaciones en los archivos y resultados reales, y mantener humana la decisión final.

### Relación con la actividad de Ingeniería de Software I

La presentación complementa la actividad de identificación y validación de necesidades en cuatro puntos: convierte la necesidad del stakeholder en un issue o historia clara; hace verificables los criterios de aceptación; permite seguir el cambio hasta sus pruebas y versión; y propone evidencia compartida para decidir cuándo el trabajo está terminado. Para completar la actividad todavía se deben entrevistar usuarios, completar la matriz de stakeholders, revisar al menos cuatro requisitos del proyecto y actualizar dos historias de Jira.
